# Alert Data Handling & Privacy

## Overview
Phase 4 introduces an alerting and triage mechanism. It is critical that this system operates with the same privacy guarantees as previous phases. Alerts are strictly a workflow management tool and do not independently retain sensitive diagnostic text or recordings.

## Data Retention
*   **Raw Audio:** The system does NOT retain any raw audio from voice check-ins. Once the audio is processed by the AI feature extraction pipeline and the check-in completes, the raw byte payload is discarded. Alert records are downstream from this process and never touch raw audio.
*   **Raw Transcripts:** Natural language processing is performed ephemerally. The alert engine only receives derived engineering summaries (e.g., "Elevated mood signal") and the final fused risk score.
*   **Database Record:** Alerts are stored in the `alerts` PostgreSQL table. The `ai_explanation` column contains a deterministic, human-readable summary generated by the Phase 3F Explainability Engine. This is safe to persist as it contains no raw PII/PHI transcripts, only engineering insights.

## Authorization
*   Counsellor authorization is strictly enforced at the API route layer via `Depends(get_current_counsellor)`.
*   A counsellor can only retrieve alerts for a `case_id` explicitly assigned to them (enforced via database join).
*   Any attempt to fetch, acknowledge, or resolve an alert belonging to an unauthorized case returns a `404 Not Found` or `401 Unauthorized`.
*   Victim access to counsellor endpoints is completely rejected by the JWT decoding layer (which verifies the token subject maps to the `counsellors` table).

## Audit Trail
*   All state changes (Acknowledgement, Resolution) are logged via the alert's `is_read`, `is_resolved`, `resolved_by`, and `resolved_at` fields.
*   Interventions or observations made by human counsellors are stored in the `case_notes` table, ensuring a complete auditable history of the decision-making process.
